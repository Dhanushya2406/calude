# Snackable — Current State

Snapshot as of `manifest.json` v2.5.0. This is a state-of-the-union, not a changelog — for the version-by-version history of how each piece got here (including full reasoning for every fix below), see `../CONTEXT.md`. For the dev loop and file layout, see `../CLAUDE.md`. This file exists so a new session doesn't have to re-derive any of the following from scratch.

## Product purpose

A personal Manifest V3 Chrome extension that turns YouTube's Watch Later playlist into an intentional watch queue — curate in advance via YouTube's native "Save to Watch Later," consume later with notes/highlights/chapters captured per video, and see time-consumption analytics by category. The core belief driving every "no" in this project: adding a video must be zero-friction (no manual URL pasting, no separate app to open), and notes/highlights — not watch time — are the actual point.

## Architecture (three parts)

1. **`background.js`** — service worker. Every 15 min (`chrome.alarms`), opens `youtube.com/playlist?list=WL` in a hidden tab, scrapes it via `chrome.scripting.executeScript` (selectors: `ytd-playlist-video-renderer`, `ytd-thumbnail-overlay-time-status-renderer` for duration — inherently fragile, YouTube can change these at any time with no warning), dedupes into `chrome.storage.local`, and separately batch-checks embeddability via YouTube's oEmbed endpoint.
2. **`dashboard.html`/`dashboard.js`/`dashboard.css`** — the entire UI, opened from the toolbar icon. One `sl-tab-group[placement="start"]` (left sidebar) with four panels: Queue, Watch, History, Analytics.
3. **`docs/player.html`** — a stateless relay page, served live via GitHub Pages at `https://dhanushya2406.github.io/calude/player.html`. Not loaded from disk by the extension at all — see "Video player architecture" below for why it has to exist.

No build tooling anywhere (no `package.json`, no bundler). UI components (Shoelace), icons (Lucide), and the typeface (DM Sans) are all vendored as static files under `vendor/`, `icons/ui/`, `fonts/dm-sans/` respectively, loaded directly — see `CLAUDE.md` for the vendoring details and the sharp edges that come with them (the Shoelace autoloader's root-relative-path requirement especially).

## Navigation implementation

**Current structure**: `sl-tab-group[placement="start"]` — a 220px left sidebar containing, top to bottom: a brand ribbon, four `sl-tab` elements (Queue/Watch/History/Analytics, each with a Lucide icon), and a footer with the "Sync now" button. The tabs' active-state indicator is **not** Shoelace's built-in one — it's fully custom (`#tabIndicator` in `dashboard.js`/`dashboard.css`): a single `position: fixed` div, measured against the active `<sl-tab>` via `getBoundingClientRect()` and animated via `transform: translateY()` + `height`, `.5s cubic-bezier(.16, 1, .3, 1)`.

**Why custom instead of Shoelace's own indicator**: tried tuning Shoelace's built-in `active-tab-indicator` twice (correct custom properties, correct transitioned properties, verified against its actual source in `vendor/shoelace/chunks/chunk.GYJIQCRZ.js`) and it still wasn't visibly animating for the user. Replaced it outright rather than keep tuning a mechanism that wasn't demonstrably working. See "Failed approaches" below for the full sequence.

**The brand ribbon** (`.sidebar-brand`, top of the sidebar): an inline SVG with a single curved `<path>` — concave bottom edge, thin on one side, deep dip, tall on the other — with `filter: drop-shadow(...)` (a plain `box-shadow` can't follow a non-rectangular shape). This was reverse-engineered from a reference screenshot that turned out, on a wider crop, to be Render.com's own dashboard chrome (a "your environment is hibernating" status banner — the copy matches their free-tier messaging verbatim). **It is confirmed-with-the-user pure decoration** carrying Snackable's own brand (popcorn icon + wordmark), not a real status — nothing in this extension hibernates or pauses. The curve path values (`M0,0 H220 V16 C160,65 80,70 0,54 Z`) are a best-effort visual approximation from a cropped screenshot, not a pixel-measured trace.

**Intended reference behavior, for context on why this took several iterations**: the user's actual ask evolved across the same reference image being sent multiple times — first read as a notification/toast card, then as a "breadcrumb bar + minimal top tabs" structural cue (which was built, shipped as v2.0.0, and later explicitly reverted), and only on the third pass clarified as specifically the curved-ribbon banner shown above, wanted as permanent sidebar decoration. The nav also round-tripped sidebar → top-nav → sidebar (v1.7.0 sidebar → v2.0.0 top nav, "exactly like this Render reference" → v2.4.0 back to sidebar, "undo the nav to side"). **If asked to change the nav again, confirm which direction before assuming** — this has reversed twice already.

**Known structural gotcha if you touch the sidebar markup**: `.sidebar-brand` and `.sidebar-footer` are slotted into `slot="nav"` alongside the real `<sl-tab>` elements (Shoelace's nav slot just renders whatever's given it, which is how they end up stacked in one visual column). But Shoelace's `getAllTabs()` (`vendor/shoelace/chunks/chunk.PKRKD3AZ.js`) does `slot.assignedElements()` with **no tag-name filtering** — anything slotted into "nav" is walked as a phantom tab by its own keyboard-navigation indexing (`this.tabs`, `findNextFocusableTab()`, Home/End). Fixed by setting `.disabled = true` (a plain JS property, not an HTML attribute, invisible on a `<div>`) on both elements right after load in `dashboard.js` — Shoelace's own `!el.disabled` filter then excludes them exactly like a real disabled tab. **Any new element added to `slot="nav"` that isn't an `<sl-tab>` needs this same treatment**, or it will silently corrupt arrow-key/Home/End navigation between the real tabs without throwing any error.

## Video player architecture

**The constraint that shapes everything here**: YouTube's player-config check rejects `chrome-extension://` as an embedding origin outright (confirmed empirically — YouTube's own player rendered "This video is unavailable — Error code 152" for multiple videos with no server-side embedding restriction on any of them, unaffected by Referer-header fixes or an explicit `origin=` param). **A Chrome extension page cannot embed a YouTube iframe directly, full stop** — this is why `docs/player.html` exists as a relay on a real `https://` origin. The Watch tab embeds that GitHub Pages page, which in turn embeds the actual YouTube iframe and relays `postMessage` traffic both directions.

**No official IFrame API** — `enablejsapi=1` is set, but the official `iframe_api` script is never loaded, because MV3's default CSP blocks remote scripts in extension pages. `dashboard.js` speaks the raw `postMessage` protocol by hand (`postToPlayer()`, the `window.addEventListener("message", ...)` handler). This means:
- No synchronous `getCurrentTime()`/`getDuration()` — the custom timeline "polls" by sending `{event:"command", func:"getCurrentTime"}` on a 500ms interval and reading the reply back out of the same `infoDelivery`-style messages already used for note/highlight timestamps.
- Player errors arrive as raw numeric codes with no built-in reliability guarantee (see "Accessibility issues" is the wrong section for this, but the error-handling logic is worth knowing: only codes 101/150 (creator disabled embedding) and 100 (video removed/private) are treated as immediately fatal; anything else gets a 4-second grace period waiting for real playback telemetry before showing a "playback failed" fallback, since this hand-rolled protocol isn't reliable enough to trust a single stray error event).

**Custom minimal timeline** (`.custom-timeline` in `dashboard.html`/`.css`, functions near `seekTo()` in `dashboard.js`): the embed URL in `docs/player.html` carries `controls=0&rel=0&iv_load_policy=3` — these suppress YouTube's own control bar, end-screen related videos, and annotations via real embed parameters, not CSS/overlay hiding (the iframe is cross-origin; there is no DOM access into it regardless, so CSS-hiding was never an option). A progress bar sits flush against the player's bottom edge (shared rounded corners, reads as one attached unit, not a separate control panel). Click/drag uses pointer events and calls the same `seekTo()` already used for chapter and note-timestamp jumps.

**What cannot be achieved, and why**: the YouTube logo/watermark cannot be removed by any embed parameter or technique — it's contractual on YouTube's side for any embed. Getting a truly chrome-free player (own `<video>` element, no watermark) would require extracting a direct video file/stream URL from YouTube, which is only possible by reverse-engineering their internal streaming API (what `yt-dlp` does) — explicitly not implemented here, since doing that to re-serve YouTube's video through a custom player is a real ToS/legal exposure, not just a technical shortcut.

**YouTube Premium ad-free playback is not guaranteed.** The embed domain is `youtube.com`, not `youtube-nocookie.com`, specifically to allow the player to recognize a logged-in Premium session (the nocookie domain never sends cookies by design, so it can never know the viewer is Premium and always shows ads). But this only works if the viewer is logged into that Google account in the same Chrome browser, and depends on Chrome's current third-party-cookie policy allowing the relay page's origin to see that login state — **this part has not been confirmed working**, only reasoned through.

## Header / scroll layout

**Current implementation**: each `sl-tab-panel` splits into two children — `.page-header` (a normal, non-positioned block; H1 + subtitle) followed by `.panel-scroll` (the *only* element with `overflow-y: auto` anywhere in the panel). `.main-tabs::part(body)` (Shoelace's own scroll container) no longer scrolls at all — `overflow-y: auto` was removed from it entirely. Each `sl-tab-panel::part(base)` is stretched to `height: 100%` and made a flex column so `.panel-scroll` can `flex: 1` and fill the remaining space below the header.

**This is a real DOM/layout separation, not `position: sticky`.** An earlier version made `.page-header` `position: sticky; top: 0` with a negative-margin trick to bleed full-width — this had a persistent bug (see "Known bugs" / "Failed approaches") where scrolled content visibly ghosted through the header, and it took three attempts to actually fix by abandoning sticky positioning altogether in favor of structural separation. **Do not reintroduce `position: sticky` for this header without reading the "Failed approaches" section below first.**

One non-obvious side effect of this structure: Shoelace sets `--padding: 0 var(--sl-spacing-medium)` on slotted `sl-tab-panel`s specifically when `placement="start"` (see `chunk.GYJIQCRZ.js`), which flows into that same `::part(base)` element's own `padding: var(--padding)` rule inside `tab-panel.styles`. This is now explicitly zeroed (`.main-tabs sl-tab-panel::part(base) { padding: 0; }`) so `.page-header` and `.panel-scroll` fully control their own horizontal inset — this baseline padding had actually been present, unnoticed, since the sidebar layout was first built.

## Accessibility issues discovered (and fixed)

1. **`aria-hidden` on an element retaining focus** (Chrome DevTools warning). Root cause, confirmed by reading Shoelace's actual source rather than assuming: `setActiveTab()` (`chunk.PKRKD3AZ.js`) never calls `.blur()` on anything — it only flips `active`/`tabIndex` on tabs and `active` on panels, then emits `sl-tab-hide`/`sl-tab-show`. Focus management during a tab switch is **entirely the consumer's responsibility**; Shoelace provides no default. Separately, `sl-tab-panel`'s `active → aria-hidden` reflection (`chunk.GMWHDCZQ.js`) goes through Shoelace's `watch()` decorator into Lit's `update()` lifecycle, which is deferred to the next microtask, not synchronous. Fix (current, in `dashboard.js`): one centralized `mainTabs.addEventListener("sl-tab-hide", ...)` handler blurs `document.activeElement` if it's contained in the panel about to be hidden — timing-proof, since `sl-tab-hide` fires synchronously, strictly before the microtask that applies `aria-hidden`. This replaced two earlier scattered `blur()` calls at specific call sites (`openWatch()`, `markWatchedBtn`) that **completely missed native tab clicks** (clicking a tab label directly never went through either of those call sites) — the centralized handler is not just cleaner, it's the only version that's actually complete.
2. **Keyboard tab-navigation corruption** from non-tab elements in `slot="nav"` — covered above under Navigation. Not a Chrome warning, silent breakage (Home/End and arrow-key nav could land on the brand/footer divs instead of real tabs) — would only surface as a user-reported "keyboard nav feels broken," never as a console message. Fixed via the `.disabled = true` property trick described above.

## Important failed approaches (do not repeat these)

- **`position: sticky` for `.page-header`**, three attempts:
  1. Sticky + negative margins to bleed full-width + `z-index`. Symptom: scrolled card/stat content visibly ghosted through the header.
  2. Diagnosed (incorrectly, or at least incompletely) as a Chrome compositor-layer bug; "fixed" with `transform: translateZ(0)` + `isolation: isolate` on the header. Bug recurred.
  3. Real cause turned out to be `.queue-grid .queue-item` having `will-change: transform` + `transform: translateZ(0)` set **unconditionally on every card, all the time** (20-40+ simultaneous GPU-promoted layers with many cards on screen) — moved to only apply during `:hover`/`:focus-visible`. This *also* didn't fully hold.
  - **Final resolution**: abandoned `position: sticky` for this entirely in favor of the structural `.panel-scroll` split described above. If a sticky header is ever wanted again anywhere in this app, budget time to verify it doesn't reintroduce this — `sl-tab-panel`'s internal `<slot part="base">` wrapper (see Header section above) is suspected as a contributing factor in why sticky positioning wasn't behaving predictably through it.
- **Shoelace's built-in `active-tab-indicator`**, tuned twice with source-verified-correct CSS (right custom properties, right transitioned properties) — replaced with a fully custom indicator rather than continue trusting a mechanism that wasn't visibly working for unconfirmed reasons.
- **Slotting the custom tab indicator into `slot="nav"`** (its first implementation) — worked visually, silently broke Shoelace's own keyboard-navigation indexing (see Navigation section above). Moved to `position: fixed` as a non-slotted sibling instead.
- **Extracting real YouTube video files for a fully custom `<video>` player** — not attempted; would require reverse-engineering YouTube's streaming API, which is a ToS/legal problem, not an engineering one. Explicitly declined rather than half-built.
- **Reading a reference image too literally on first pass**: the sidebar's warm dark palette was briefly abandoned for a literal white card background (matching a reference screenshot's light-mode colors exactly) before being reverted — the *structural* pattern from a reference is usually the ask, not its literal colors, when the rest of the app is already themed.

## Current known bugs / unconfirmed behavior

- **Cross-device sync is broken.** The entire reason this project is a Chrome extension (vs. e.g. a web app) was to get free cross-device sync via `chrome.storage.sync`. The actual code uses `chrome.storage.local` everywhere (queue, notes, highlights, analyticsTotals) — likely swapped in at some point to dodge `storage.sync`'s ~100KB quota once payloads grew. **This means the core "add from phone, see it on desktop" promise does not currently hold.** This is the single most important open issue in the project.
- **YouTube Premium ad-free playback is unconfirmed** — see Video Player section above.
- **Chapters are best-effort and will silently stop working** if YouTube changes its watch-page internal JSON structure (`extractChaptersFromWatchHtml()` in `dashboard.js` walks an undocumented internal shape). Same fragility class as the `background.js` scraper.
- **`background.js`'s scraper selectors** (`ytd-playlist-video-renderer` etc.) will break silently if YouTube changes its DOM — no error surfaces, videos just stop appearing on sync.
- **`analyticsTotals` heartbeat is coarse** — +30s is credited every 30s the Watch tab is open on a video, regardless of whether the tab is actually backgrounded or the video is actually playing.
- **The brand ribbon's curve is an unverified visual approximation** (see Navigation section) — may need retuning once compared closely against pixel measurements of the original reference.
- **No mobile-viewable dashboard** — Watch Later additions from the mobile app land in the queue fine on next sync (that data is account-wide), but there's no way to view/use the dashboard itself outside this desktop Chrome extension.

## Design decisions that must be preserved

- **No manual URL pasting, ever.** Adding a video must stay zero-friction via YouTube's native "Save to Watch Later" — this is non-negotiable per the user, not just a current implementation detail.
- **No cookie scraping.** Explicitly considered and rejected (pulling account cookies to auth as the user is a real security tradeoff that was deliberately ruled out) — do not suggest this as a fix for the sync issue or anything else.
- **No external backend/database.** One narrow, already-approved exception: `docs/player.html` on GitHub Pages, which is stateless (pure `postMessage` relay, no storage, no server logic) — this doesn't violate the spirit of the rule and shouldn't be treated as an opening to add more server-side pieces.
- **Notes/highlights are the point, not watch time.** Any feature work that trades off note/highlight capture quality for something else (e.g., smoother playback, more analytics) is going against the core product thesis.
- **Warm, fintech-inspired dark palette** (`:root` custom properties in `dashboard.css` — `--bg`, `--surface`, `--accent`, etc.) is the established visual identity. Reference screenshots should be read for structural/interaction patterns, not literal colors, unless explicitly told otherwise (see "Failed approaches").
- **Move fast, keep it simple.** The user has said this directly and repeatedly — no over-engineering, no infra for its own sake, no scope creep beyond what's asked.
